Developer Implementation Brief

FST Online System

Complete implementation instructions for the Poster Gallery, Secretary Workspace, mobile-first PWA, publishing workflow, privacy, and quality assurance.

OrganizationCalvary Foursquare Church (CFC)
HostingGitHub Pages
PlatformResponsive website / PWA
PublishingAuthorized Secretary via GitHub workflow

Project objective

Update the existing Funeral Service Team (FST) Online System into a professional, mobile-friendly application for viewing and managing approved funeral and memorial service information.

The Poster Gallery must be integrated into the existing app, not built as a separate website. Preserve existing working features and data. Inspect the current source code and create a backup or Git branch before changing files.

HTML / CSS / JavaScript JSON files GitHub Pages PWA No Firebase No Google Sheets

1. Existing features to preserve

  • Dashboard
  • Upcoming and completed memorial services
  • Calendar and event details
  • Team assignments
  • Published financial summaries
  • Announcements
  • Secretary Workspace and JSON export workflow
  • Installable PWA behavior and best-effort offline viewing

Do not remove or redesign existing functionality in a way that breaks current workflows. Reuse existing scripts and styles where possible.

3. Poster Gallery — public interface

Add a visible Poster Gallery or Posters section to the main navigation and dashboard.

Poster cards

  • Show a thumbnail, title, category, optional event date, and optional short description.
  • Use a responsive grid: one or two columns on phones depending on screen width, more columns on larger screens.
  • Preserve the original poster aspect ratio. Never crop important text or faces.
  • Make the whole card easy to tap, with readable captions and sufficient spacing.
  • Show only records marked as published.
  • Provide a clear empty state when there are no published posters.

Suggested categories

  • Memorial Service
  • Funeral Service
  • Church Announcement
  • Team Meeting
  • Training and Workshop
  • Other

Add category filtering and text search if practical, without making the mobile interface crowded.

Poster detail viewer

When a poster is tapped, open an accessible modal or detail page that shows the full image, title, category, description, event date, venue, and related event link when those values exist.

  • Provide a visible close button and Escape-key support where available.
  • Keep the image within the viewport; allow scrolling or zooming on small screens.
  • Use meaningful alt text.
  • Show a fallback if the image fails to load.
  • Do not invent missing dates, times, venues, names, or other event facts.

4. Poster data file and schema

Create data/posters.json. Use the following schema consistently in all JavaScript and admin forms:

[
  {
    "id": "poster-example-001",
    "title": "Memorial Service Announcement",
    "category": "Memorial Service",
    "image": "assets/posters/memorial-example.jpg",
    "description": "",
    "date": "",
    "venue": "",
    "eventId": "",
    "status": "published",
    "publishedAt": "",
    "alt": "Memorial service announcement poster"
  }
]
Important: This is an example record only. Do not publish fictional event information as an actual CFC announcement. Use real, approved data.

Implementation rules:

  1. Every poster must have a unique, stable ID.
  2. The image path must reference a real image file in the repository.
  3. Optional fields may be empty or null; the app must not crash.
  4. Only status: "published" records appear in the public gallery. Draft records remain hidden.
  5. Validate JSON and show a readable error if it is malformed.
  6. Handle missing files and image-load failures gracefully.
  7. Sort records predictably, preferably by publication date, with upcoming events optionally prioritized.
  8. Use relative asset paths that work under GitHub Pages project-site URLs. Do not assume the site is hosted at the domain root.
  9. Safely render user-provided text. Do not insert untrusted values using unsafe HTML injection.
  10. Use the exact property names above consistently. The top-level JSON value must be an array, matching the existing app and Secretary JSON Editor. For compatibility, records without a status field are treated as published; new records should explicitly use "draft" or "published".

5. Secretary Workspace — poster management

Extend the existing admin.html and js/admin.js. Do not replace the administration interface unnecessarily.

Form fields

  • Poster title (required)
  • Category (required)
  • Image path (required)
  • Description (optional)
  • Event date (optional)
  • Venue (optional)
  • Related event ID (optional)
  • Alternative text (recommended)
  • Publication status: draft or published

Required actions

  • Add a poster record.
  • Edit an existing record.
  • Remove a record from the prepared dataset.
  • Preview the selected poster.
  • Mark a poster as draft or published.
  • Export the complete, valid posters.json file.

Validate required fields, duplicate IDs, and image paths before export. Show clear success or error messages. Preserve all other records when one poster is added or edited. The preview should show the image before export.

6. Publishing workflow and GitHub limitation

Critical: GitHub Pages is static hosting. A normal browser form cannot directly write new files into the GitHub repository. Do not claim that a Publish button automatically updates the live website unless a secure, real publishing mechanism has been implemented and tested.

The initial implementation must use this workflow:

  1. The Secretary prepares or edits poster records in the browser.
  2. The Secretary downloads the generated posters.json.
  3. The Secretary uploads the actual image files to assets/posters/ in the GitHub repository.
  4. The Secretary replaces or updates data/posters.json.
  5. The Secretary commits the changes to GitHub.
  6. GitHub Pages deploys the update.
  7. Team members see the new posters after deployment and any necessary cache refresh.

The existing client-side demo PIN is not secure authentication. A PIN embedded in JavaScript can be discovered. Repository permissions determine who can directly modify and publish the GitHub repository.

Never embed a GitHub personal access token or other secret in client-side JavaScript. If direct publishing from the phone is required in a future phase, implement a secure authenticated backend or GitHub integration with proper permission controls.

7. Dashboard integration

  • Add a “Latest Posters” preview to the dashboard.
  • Display a few recent published posters.
  • Provide a “View All Posters” link to the gallery.
  • Make thumbnails readable and responsive on phones.
  • Show a friendly empty state when no posters are published.
  • If a poster links to an existing event, allow navigation to that event's details.
  • Avoid showing the same poster more than once in the dashboard preview.

The gallery must not replace or break the existing dashboard, calendar, assignments, announcements, or finance-summary sections.

8. Image asset requirements

Support JPEG/JPG, PNG, and WebP. SVG may be used for trusted vector artwork such as logos and icons.

  • Use lowercase filenames and hyphens instead of spaces.
  • Compress large images before uploading.
  • Keep the poster's original proportions.
  • Use object-fit: contain where needed so poster text is not cropped.
  • Use descriptive filenames, for example:
assets/posters/memorial-service-october.jpg
assets/posters/team-meeting.png
assets/posters/evangelism-training.webp

Placing an image in the folder does not automatically add it to the gallery. It must also have a valid record in data/posters.json.

9. Mobile-first PWA and offline behavior

Preserve manifest.webmanifest, service-worker.js, and js/pwa.js. Update their references only as needed.

  • Responsive layout, touch-friendly controls, readable typography, and navigation for narrow screens.
  • Accessible color contrast and spacing around device edges.
  • Fast loading on mobile connections.
  • Clear loading, empty, and error states.
  • Cache the app shell and public JSON, including data/posters.json.
  • Cache only a reasonable subset of poster images; do not cache every large image indiscriminately.
  • Provide a graceful fallback when an image is unavailable offline.
  • Implement cache versioning and remove obsolete caches when appropriate.
  • Test that new poster data and images can be retrieved after deployment without asking users to clear all browser data.

Offline viewing is best-effort. A device must visit the site online at least once, and new posters require an internet connection before they can be downloaded to that device.

10. Privacy and security

  • Publish only information approved for public viewing.
  • Obtain permission before publishing family photographs or personal details when appropriate.
  • Never store private identity documents or confidential family records in public asset folders.
  • Do not publish detailed financial information unless specifically approved for public access.
  • Keep internal-only records out of public JSON files.
  • Do not treat hidden interface elements or a client-side PIN as access control.
  • Never embed credentials, private tokens, or secrets in browser JavaScript.
  • Do not add an unauthenticated endpoint that can modify repository content.

Files hosted publicly by GitHub Pages may be accessible to anyone who has the relevant URL. Design all published data with that limitation in mind.

11. Performance and accessibility

  • Lazy-load poster thumbnails where appropriate.
  • Set image dimensions or aspect ratios to reduce layout shifts.
  • Use meaningful alternative text.
  • Give buttons accessible names and ensure keyboard usability where applicable.
  • Keep modal controls accessible and visible.
  • Avoid unnecessary external dependencies.
  • Prefer repository-hosted images when practical.
  • Show a friendly message if poster data cannot load.
  • Ensure all gallery controls work on small screens.

12. Acceptance test checklist

Poster Gallery

  • Gallery loads from data/posters.json.
  • A published poster appears.
  • A draft poster is hidden from public view.
  • Tapping a poster opens the full-size view.
  • Closing the viewer returns to the gallery.
  • Search and category filters work, if implemented.
  • Missing images display a fallback instead of breaking the page.
  • Optional dates, venues, and descriptions can be empty.
  • Invalid JSON displays a readable error rather than a blank application.

Secretary Workspace

  • A new poster record can be prepared.
  • An existing record can be edited.
  • A record can be saved as draft or marked published.
  • Export produces valid JSON.
  • Export does not unintentionally delete other records.
  • Duplicate IDs are detected.
  • Preview shows the intended image.
  • Manual GitHub publishing instructions are clear.

Existing app and deployment

  • Dashboard, calendar, event details, assignments, announcements, and financial summaries still work.
  • PWA installation still works.
  • No JavaScript errors occur during normal navigation.
  • GitHub Pages project URLs and repository-relative asset paths work.
  • Offline mode works within the tested cache limits after an initial online visit.
  • New poster data is retrieved after deployment and cache refresh.
  • No false claim of automatic publishing or real-time synchronization is made.

13. Delivery requirements

Deliver all of the following:

  1. Complete updated source code.
  2. Updated data/posters.json.
  3. Any new or updated CSS and JavaScript files.
  4. Updated service-worker cache rules.
  5. Updated README.md with installation, poster upload, and publishing instructions.
  6. A list of files created or modified.
  7. Screenshots of the actual running application at a mobile viewport.
  8. A test report showing passed and failed acceptance tests.
  9. A clear explanation of known limitations.

Do not deliver only a visual mockup. The Poster Gallery must function in the actual application.

14. Definition of done

The project is complete when the Secretary can prepare a poster record, place the actual poster image in the correct assets folder, export valid JSON, publish both files through GitHub, and see the poster appear in the public FST app after deployment.

Team members must be able to open the poster on their phones, view its details, and navigate to the related event when applicable. All existing application features must remain functional.

Final instruction to the developer

Do not rewrite the entire app before inspecting the existing code. Preserve working features, integrate the Poster Gallery cleanly, test the actual GitHub Pages deployment, and report honestly what has and has not been implemented.
